Desktop updates use Tauri's updater plugin. The endpoint and public verification
key live in `tauri/src-tauri/tauri.conf.json`. This fork still points at
`jamiepine/voicebox` releases, so an upstream update does not necessarily preserve
fork changes. Identify the actual build/commit when testing a fix.

## Desktop update flow

The shared UI calls its platform updater contract. The desktop implementation in
`tauri/src/platform/updater.ts` checks the configured release manifest, reports
available versions and download progress, downloads a signed package, and applies
it through the Tauri plugin. Restart behavior is platform-specific; the Windows
installer handles its restart. Browser clients do not use the desktop updater.

The release manifest contains a version and per-platform download/signature
information. A build needs a higher released version to be offered as an update;
two different commits with application version `0.5.0` are not distinguishable
by a version comparison alone.

## Signing and release ownership

The public key is safe to distribute. The matching private key and optional
password are supplied through `TAURI_SIGNING_PRIVATE_KEY` and
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in the release environment. Never commit the
private key or bypass verification after an invalid-signature error.

`.github/workflows/release.yml` defines artifact creation and publication.
Use the project's changelog/version/release workflow for a new release instead of
publishing an arbitrary tag. Repointing a fork's updater requires an intentional
release channel, signing setup, and a tested manifest for each supported target.

## CUDA and ROCm backends

GPU backends are installed separately from the desktop update package. On
supported Windows installations, Settings can download a server-core archive
and a versioned CUDA or ROCm library archive. Matching libraries can be reused
when only the server core changes. Consult the download response for actual sizes.

| Component | Source |
| --- | --- |
| CUDA status, download, update policy | `backend/services/cuda.py` |
| ROCm status, download, update policy | `backend/services/rocm.py` |
| Shared bounded downloads, checksums, safe extraction/install | `backend/utils/backend_archive.py` |
| HTTP/SSE endpoints | `backend/routes/cuda.py`, `backend/routes/rocm.py` |
| Archive packaging | `scripts/package_cuda.py`, `scripts/package_rocm.py` |

Installed packages live at `<data-root>/backends/cuda/` or
`<data-root>/backends/rocm/`. Downloads require a valid SHA-256 checksum and bounded
archive validation. Interrupted installations have recovery logic; checksums from
the release source provide integrity and are distinct from Tauri package signatures.

## API

| Method | CUDA path | ROCm path |
| --- | --- | --- |
| GET | `/backend/cuda-status` | `/backend/rocm-status` |
| POST | `/backend/download-cuda` | `/backend/download-rocm` |
| GET (SSE) | `/backend/cuda-progress` | `/backend/rocm-progress` |
| DELETE | `/backend/cuda` | `/backend/rocm` |

Use the [API reference](/api-reference) for response schemas and server
authentication. Backend installs, removals, and model operations enforce their
operation guards; do not replace files manually while generation is active.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| No desktop update offered | Current version, configured endpoint, and release target assets |
| Invalid signature | Manifest signature, matching public/private key, and uploaded artifact |
| Download or checksum failure | Release asset/checksum availability, network access, and free disk space |
| Fork fix seems missing | Actual installed commit/build and upstream updater channel |
| GPU backend is unavailable | Supported OS/device and engine runtime; see the GPU guide |

See [building](/developer/building), [GPU acceleration](/overview/gpu-acceleration),
and [storage](/overview/storage-and-backup) for setup and data locations.
