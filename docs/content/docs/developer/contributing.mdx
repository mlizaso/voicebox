## Start from the repository guides

The root `README.md` is the complete operating guide. `CONTRIBUTING.md` defines
setup, contribution scope, validation commands, build outputs, and release-note
maintenance. Keep those entry points current when behavior changes.

Use [development setup](/developer/setup) and [architecture](/developer/architecture)
for the source/runtime map. Use the generated API reference for current field
names; the application client itself is handwritten under `app/src/lib/api/`.

## Keep changes reviewable

- Start from a concrete behavior, failing scenario, or maintenance problem.
- Keep shared UI behind the platform contract and authenticated client boundary.
- Preserve database/file ownership and legacy compatibility when adding fields.
- Test cancellation, failure, connection changes, and import validation where relevant.
- Preserve audio quality and exact-runtime checks; validate numerical/performance
  changes using the same model, input, references, and processing settings.
- Update usage docs and `[Unreleased]`, preserving dated release/audit history.

## Validate

```bash
bun run ci
backend/venv/bin/python -m pytest backend/tests -q
just check-python
bun run check
```

Run focused checks first. Native, docs, landing, and frozen-model checks are
separate and listed in `CONTRIBUTING.md`, `docs/README.md`, and
`backend/tests/README.md`. Existing repository-wide lint debt is not a reason to
suppress new diagnostics or reformat unrelated files.

Describe what changed, why, which checks passed, and what remains untested.
Use the repository's recent commit style, such as
`fix(history): preserve generation settings on retry`. Keep tokens, database
files, and private voice references out of commits.
