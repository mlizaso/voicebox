The desktop build combines a shared React frontend, the Rust/Tauri shell, and
Python sidecars. Build this checkout to include its fork changes. The configured
updater still targets upstream releases; the shared application version alone
does not identify every later commit.

## Commands

Run these after `just setup`, from the repository root:

| Command | Result |
| --- | --- |
| `just build` | Backend sidecars and desktop bundle |
| `just build-server` | Server and MCP sidecars |
| `just build-tauri` | Desktop bundle using prepared sidecars |
| `just build-web` | Browser client in `web/dist/` |
| `bun run build:landing` | Independent Next.js landing site |

The docs site has its own Bun workspace and build command. Frontend builds do
not create Python sidecars, native installers, or the private audiobook workspace.

Desktop builds require Rust and the platform's native tools. On this Mac, Xcode
may need to be selected with
`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` for `actool`. Keep the
Python environment and pinned MLX dependencies aligned with the source revision.

## Python sidecars

`scripts/build-server.sh` invokes `backend/build_binary.py` and copies artifacts
with their Rust target suffix into `tauri/src-tauri/binaries/`:

- `voicebox-server`: FastAPI, model backends, and runtime dependencies.
- `voicebox-mcp`: a small stdio shim that forwards JSON-RPC to the running server.

The backend entry point is `backend/server.py`. Ordinary server builds use
PyInstaller `--onefile`; CUDA and ROCm builds use `--onedir` so the server core
and heavy libraries can be packaged separately. The build configuration owns
hidden imports, package metadata, runtime hooks, and native data files such as
MLX libraries and Metal resources.

When modifying an engine, verify frozen imports and a real model request in the
resulting bundle. A source-environment import is insufficient to validate
PyInstaller packaging. See [engine integration](/developer/tts-engines).

## GPU backend packages

Windows has repository recipes including `just build-server-cuda` and
`just build-local`. `backend/build_binary.py` also accepts `--cuda` or `--rocm`
for a correctly prepared build environment. `scripts/package_cuda.py` and
`scripts/package_rocm.py` create the separate server/library archives and checksums.
The release workflow defines the corresponding toolchains and dependency setup.

The application installs these under the backend data root's `backends/` directory.
It does not treat a downloaded archive as ready until integrity and installation
checks complete. See [updating](/developer/autoupdater).

## Desktop bundle and signing

`tauri/src-tauri/tauri.conf.json` declares both external binaries under its
top-level `bundle` configuration. Tauri builds the frontend, compiles Rust, and
places platform bundles beneath `tauri/src-tauri/target/release/bundle/`.
Available installer formats depend on the platform and release configuration.

`.github/workflows/release.yml` defines CI packaging, signing, and uploaded assets.
Signing credentials belong in the configured secrets store. Ordinary source
changes update `[Unreleased]` in `CHANGELOG.md`; version stamping, tags, and
publication belong to the separate release workflow.

## Validation before distributing

Run the checks for the changed surface from root `CONTRIBUTING.md`: shared tests,
TypeScript, import boundaries, frontend builds, backend regressions, and relevant
native tests/format checks. Then launch the actual packaged artifact, verify its
data root and server lifecycle, and exercise the affected model/native feature.
Do not bypass signature, exact-runtime, or storage-integrity checks to make a
build appear functional.
